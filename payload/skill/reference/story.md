# 使用故事與圖清單

- 編號與命名

## 為什麼先寫故事

圖序、章節、哪些畫面要拍，都由故事決定，不由程式碼的分支數量決定。
故事讓每張圖都有「為什麼拍」的理由，也讓圖與圖之間的資料自然連貫（同一個主角、同一批資料）。

## USER_STORY.md 的寫法

- 用**文章段落**寫，不用條列：主角是誰、要完成什麼、一步一步做了什麼。
- 每個要拍的畫面都要在故事裡被提到；故事沒提到的畫面不拍。
- 一個段落可以介紹多張圖，不必一張圖一段。
- 步驟照使用者實際會做的順序，不跳步。要建立一份最終結果，就從空白開始一步步建。
- 開頭不放登入頁，除非登入本身是這個系統獨有的功能；優先介紹只屬於這個系統的功能。
  使用者明確要求「從登入開始」時，以使用者為準：登入寫成簡短的一段、只拍一張，並在清單確認時註明。
- 主角、單位、日期、數量等會顯示在畫面上的事實，先列在故事開頭，並同步寫進 `facts.json`。
- 沒有故事時，先和使用者一起寫：問使用者是誰在用、要完成什麼；從程式的路由與頁面確認有哪些功能；寫完給使用者看過再往下。

## 由故事導出圖清單

1. 依故事順序，把每個被提到的畫面列成一筆。
2. 再補故事沒明講但手冊需要的狀態：空資料、錯誤、驗證失敗、權限不足、開啟的對話框或抽屜、長內容。純 hover 或 focus 的樣式除非必要不拍。
3. 為每筆標 `kind` 與 `stability`（定義見 [stale.md](stale.md) 與 [stability.md](stability.md)）。
4. 區分兩種步驟：「展示功能的圖」要拍；「只為了走到下一頁的準備」標 `setup`，由檢查點提供狀態，不放進圖序。
   檢查點已經替你建好資料時，展示「新增」功能的圖仍然要拍，不要因為可以直接進入後面的頁面就把它省掉。

## 編號與命名

- id 是 kebab-case 英文，唯一，也是 PNG 檔名；圖說用中文。
- 章節用數字，圖在章內用有間隔的編號（`010`、`020`、`030`），之後插圖不必整批改名。
- 需要子圖時，在 manifest 用 `parent` 指向主圖，不把 `(a)(b)` 塞進 id。

## 給使用者確認的清單格式

用表格列出，一次給完，等使用者回覆後才開始拍：

| 章 | id | 圖說 | kind | stability | 需要的前提 |
|---|---|---|---|---|---|
| 1 | 010-schedule-empty | 尚未建立班表 | main | stable | 已登入 |
| 3 | 030-solver-result | 求解器完成後的結果 | main | volatile(solver) | 已有需求資料 |

使用者要調整時直接改表，不重新解釋整份清單。
